Another `runningDeadlineSeconds` case, this time with a fresh, unique backup name and no storage errors (operator 1.20.0, ~99 GB dataset on network volumes):

- `bk100g` was created at 15:13:16. The job started and uploaded normally; S3 shows `logical size: 98751885730` for `p3/cluster1-...-15:13:16-full`, so the upload was essentially complete.
- The `PerconaXtraDBClusterBackup` stayed in `Starting` the whole time. At 15:35:51 the operator logged `Backup didn't start running in runningDeadlineSeconds, failing the backup {"runningDeadlineSeconds": 1200, "passedSeconds": 1355.8}` / `running deadline exceeded, deleting the job and its pods`. The backup became `Failed` (`running deadline seconds exceeded: deadline exceeded`), and the ~99 GB partial backup was left in the bucket.
- An identical retry (`bk100g2`) moved to `Running` within ~30 s and `Succeeded` in 2161 s. So the stuck-in-`Starting` state is intermittent. `getPXCBackupStateFromJob` / `checkJobPodsRunning` should have reported `Running` from the job's `ready=1`, but the status was never updated during those 22 minutes.

So any backup that runs longer than `runningDeadlineSeconds` is killed whenever its status misses the `Starting` -> `Running` transition. With large datasets that wastes hours of upload, and it leaves orphaned data behind. Suggestions: base the deadline check on the job's pod state directly (not only on `cr.Status.State`), and never kill a job whose pod has been Running/Ready. Also delete the partial backup when failing it.
