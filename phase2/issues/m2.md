**Environment:** mariadb-operator 26.10.1 (upgraded from 26.6.0), MariaDB 12.3.3, MaxScale 23.08.13-2, 3-replica Galera + 3 MaxScale, k3s v1.37.1, 3 workers (2 vCPU / 4 GB), local-path storage, ~8.9 GB dataset, sysbench oltp_read_write at 50 tps plus a 5 writes/s probe. Hands-on evaluation, 2026-10-14/15.

## Summary
With a realistic dataset (~9 GB), a member that needs a full SST **can never rejoin** using the default probes. The startup probe (`initialDelaySeconds 20, periodSeconds 10, failureThreshold 3`, ~50 s) kills the joiner mid-SST (exit 137), so it crash-loops forever. We saw 42 restarts over ~2.5 h after an OOM kill on that node.

Making it worse:
1. `spec.startupProbe: {failureThreshold: 180}` on the MariaDB CR was **not propagated** to the StatefulSet for 40 min while the cluster was Not ready. The STS template kept failureThreshold 3, with `updateStrategy: OnDelete`. So the documented way to fix it does not work in exactly the situation that needs it.
2. After patching the StatefulSet by hand and deleting the pod, the member completed SST + IST in 1293 s and all 3 members were Synced with the same UUID. But the CR stayed `GaleraReady=False` / `Galera not ready` for 15+ min with no operator log activity. A `User` CR created meanwhile was never reconciled. Restarting the operator fixed both (CR Ready 372 s later).

Joiner log excerpt:
```
WSREP_SST: [INFO] Proceeding with SST ... Waiting for SST streaming to complete!
Container mariadb failed startup probe, will be restarted
Last State: Terminated  Reason: Error  Exit Code: 137
```

## Expected
- Probes should account for SST, e.g. pass while `wsrep_local_state` is JOINER or an `sst_in_progress` file exists, or the defaults should be sized for multi-GB SSTs.
- Probe/spec changes should reach the StatefulSet even when the cluster is unhealthy.
- Status reconciliation should not stall after the cluster recovers.
