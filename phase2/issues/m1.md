**Environment:** mariadb-operator 26.10.1 (upgraded from 26.6.0), MariaDB 12.3.3, MaxScale 23.08.13-2, 3-replica Galera + 3 MaxScale, k3s v1.37.1, 3 workers (2 vCPU / 4 GB), local-path storage, ~8.9 GB dataset, sysbench oltp_read_write at 50 tps plus a 5 writes/s probe. Hands-on evaluation, 2026-10-14/15.

## Summary
A `kill -9` of **one** `mariadbd` (the MaxScale primary) under load led the operator to declare the whole Galera cluster unhealthy and run full-cluster recovery (downscale + restart of all pods). A single-member crash became a **155 s total write outage**. The same test in the run before cost 15 s; the run after, 8 s.

## Timeline (operator log, attached excerpt)
- T+0 s: `kill -9` mariadbd on mariadb-galera-0 (kubelet restarts the container; it rejoins via SST/IST).
- T+75 s: `galera.health  Galera cluster is not healthy`
- T+75 s: `galera.recovery  Recovering cluster` -> `Downscaling cluster` -> `Recovered Galera state` -> `Upscaling cluster` -> `Restarting Pods`
- Clients through MaxScale: `ERROR 1815 (HY000): Internal error: Session creation failed` for 140 s.

Recovery settings are the defaults: `clusterHealthyTimeout: 30s, minClusterSize: 1, clusterMonitorInterval: 10s`.

## Expected
With 2 of 3 members still Primary/Synced (one restarting, one possibly donor), the cluster is not "unhealthy" in a way that warrants restarting all members. Full recovery should only run when no Primary component exists. Treat a donor/joiner pair as transitional, or count Primary-component members rather than Ready pods.
