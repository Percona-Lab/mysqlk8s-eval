**Environment:** mariadb-operator 26.10.1, MariaDB 12.3.3, `replication.enabled: true` (semi-sync on, `primary.autoFailover: true`, `autoFailoverDelay: 0s`), 3 replicas, `pointInTimeRecoveryRef` set, k3s v1.37.1, local-path. Hands-on evaluation 2026-10-15.

## Summary
Three problems with the async replication topology after failures:

1. **No failover when the primary's node is lost.** Hard power-off of the node running the primary (mariadb-repl-1) at 00:47:12Z gave **434 s** of write outage through `mariadb-repl-primary`. It ended only when the node rebooted (00:53:14Z) and the old primary came back. No replica was promoted while the node was down. The operator's "Configuring primary" messages appear only after the node returned. (`kill -9` of mariadbd on the primary, by contrast, failed over in 2.1 s with no lost acknowledged writes.)
2. **Old primary cannot rejoin after failover.** After the `kill -9` failover, the former primary (mariadb-repl-0) crash-loops:
   ```
   Slave I/O: Got fatal error 1236 from master when reading data from binary log: 'Error: connecting slave requested to start from GTID 0-10-132, which is not in the master's binlog.
   ```
   It has an un-acknowledged transaction the new primary never received. A manual rebuild is needed; the operator doesn't detect or re-clone it.
3. **Binlog archival breaks after the crash.** The MariaDB CR goes `Ready=False` with:
   ```
   Error archiving binlogs: error uploading binary log mariadb-repl-bin.000002: error getting binary log mariadb-repl-bin.000002 metadata: error getting binlog metadata: invalid event size 0, must >= 19
   ```
   This stops PITR archiving. It looks like a preallocated/partially written binlog after a crash.

## Expected
Promote a replica when the primary pod's node is NotReady/unreachable (with fencing), re-clone diverged replicas automatically or report it clearly, and skip/tolerate a truncated trailing binlog during archival.
