Same behaviour reproduced on **1.2.0** with a different, more common trigger: a plain `kill -9` of mysqld on the **primary** (k3s v1.37.1, 3 GR members, MySQL Router, 50 tps sysbench + 5 writes/s probe, during a 6 h soak test).

Timeline (UTC, 2026-10-15):
- 19:39:55 `kill -9` mysqld on primary ps-cluster1-mysql-0; GR elects mysql-1; writes back after 34 s.
- 19:40:30 operator: `Removing primary label from pod ps-cluster1-mysql-0` / `Assigning primary label to pod ps-cluster1-mysql-1`.
- 19:41:10 `Crash recovery  Pod is waiting for recovery` -> `Attempting to reboot cluster from complete outage`.
- 19:41:11 `Tried to reboot the cluster but MySQL says the cluster is already online. Deleting all MySQL pods.`
- Result: **second, total outage of 357 s** (all 3 pods recreated) on a cluster that had already failed over correctly. No acknowledged writes were lost.

Earlier in the same run, three deliberate full-cluster crashes recovered in 139 / 209 / 362 s.

`main` (`pkg/controller/ps/crash_recovery.go`) now checks `clusterOnlineFromPods` and only restarts pods with stale markers ("Deleting pods with stale full cluster crash markers"), which looks like it addresses this. It would be good to ship it in a 1.2.x patch release, since any crash of a single member can trigger it.
