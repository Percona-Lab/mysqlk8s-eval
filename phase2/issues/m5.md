**Environment:** mariadb-operator 26.10.1, MariaDB 12.3.3, multi-cluster with `replication` topology in one Kubernetes cluster (k3s v1.37.1), manifests adapted from `examples/manifests/multi-cluster/replication` (2 replicas per cluster, shared root Secret and server CA, physical backup bootstrap via S3, ClusterIP primary Services, no MaxScale). A probe inserts ~4 rows/s through `mariadb-eu-south-primary`. Hands-on evaluation 2026-10-17.

## 1. Replica cluster never becomes Ready (second member crash-loops)
`mariadb-eu-central-0` bootstrapped from the PhysicalBackup and replicated from eu-south fine. `mariadb-eu-central-1` crash-loops (11+ restarts, liveness probe) with:
```
Got fatal error 1236 from master when reading data from binary log: 'The binlog on the master is missing the GTID 0-10-5 requested by the slave (even though both a prior and a subsequent sequence number does exist), and GTID strict mode is enabled'
```
`status.replication` showed central-1 at `gtidCurrentPos 0-10-5,1-20-2` while central-0's binlog has no domain-0 history from before its bootstrap. `mariadb-eu-central` stayed `Not ready`.

## 2. Documented cluster switchover diverged the clusters
Following "Cluster switchover" in docs/multi-cluster.md:
1. 00:12:41 `spec.maintenance.enabled: true` on eu-south (CR shows `Maintenance`).
2. `secondsBehindMaster` on central-0 reported 0; patched `spec.multiCluster.primary: mariadb-eu-central` on both CRs.

Observed:
- eu-south's primary **kept accepting application writes** through `mariadb-eu-south-primary` for the next 15+ minutes. Maintenance mode did not fence direct (non-MaxScale) clients.
- Replication into central-0 stopped at ~00:17:56 (operator: "Resetting primary replica connection" / "Reconfiguring primary GTIDs").
- central-0 became writable (`read_only=OFF`) only after ~15 min.
- Final state: eu-south-0 `read_only=OFF`, 5,665 rows, now *also* replicating from eu-central. eu-central-0 `read_only=OFF`, **3,390 rows**, `gtid_current_pos 1-20-6156` (no domain 0). **2,275 acknowledged rows written to the old primary are missing on the new primary**, and both clusters accept writes (split-brain).

## Expected
The switchover should make the old primary read-only (or otherwise fence it) before promoting, wait for the replica to apply everything, and refuse to complete while the replica cluster is not Ready. The status should not report `secondsBehindMaster: 0` while replication has stopped.
